# ColorTags Explorer — рабочая дорожная карта v3

Дата обновления: 2026-09-23

## 1. Цель ближайшей версии

Сначала получить полезный и устойчивый интерфейс в стандартном Windows 11
Explorer:

```text
Name              Tags
brief.pdf         🔴
references        🟢
archive.zip       ⚪
```

Цвет кружка в колонке должен совпадать с цветом иконки в контекстном меню.
Хранилище продолжает содержать стабильные идентификаторы `red`, `green` и
т. п. Emoji, подписи и иконки являются только представлением значения.

Полная окраска строки остаётся дальнейшим улучшением. Она не должна блокировать
колонку, меню или надёжность хранения тегов.

## 2. Подтверждённое текущее состояние

- Семь цветов и состояние `none` реализованы в Core.
- ADS работает для файлов и папок на NTFS.
- SQLite используется как fallback и больше не переносит тег на другой файл
  при повторном использовании пути.
- Современное контекстное меню умеет назначать и снимать тег, включая
  множественный выбор.
- Цветные ресурсы для меню уже существуют.
- COM DLL собирается; 75 Python-тестов проходят.
- `System.Keywords` является штатной колонкой Tags и имеет тип
  `Multivalue String`.
- UI Automation вместе с Shell API сопоставила 28 из 28 реализованных строк
  тестового окна Explorer с файловыми путями. Этот путь остаётся резервом для
  внешнего визуального слоя.
- Семь Shell icon overlay использовать нельзя: системные слоты уже заняты и
  этот механизм конфликтует с OneDrive, Google Drive и другими клиентами.

## 2.1. Прогресс этапа 1 — 23 сентября 2026

- `System.Keywords` возвращается как корректный `VT_VECTOR | VT_LPWSTR`.
- Все семь ADS-значений преобразуются в `🔴 🟠 🟡 🟢 🔵 🟣 ⚪`; обратно в ADS
  по-прежнему записываются только стабильные идентификаторы цветов.
- Найдена причина пустой колонки: Explorer не загружал COM-класс property
  handler, зарегистрированный только в HKCU. Изолированный тест подтвердил,
  что CLSID должен быть доступен из `HKLM\Software\Classes\CLSID` вместе с
  современным mapping `PropertySystem\PropertyHandlers`.
- Штатные register/unregister-скрипты теперь симметрично добавляют и удаляют
  HKLM CLSID. Массовая перерегистрация расширений пока не выполнялась.
- В отдельном процессе Explorer колонка `Tags` возвращает все семь кружков.
  Удаление и повторное назначение тега обновляют значение после
  `SHCNE_UPDATEITEM` без перезапуска Explorer.
- Визуальный гейт не пройден: Windows 11 Details View принудительно рисует эти
  emoji монохромными glyph. Значения различаются, но цвет теряется. Расширять
  emoji-вариант на реальные расширения не нужно.

## 3. Правила реализации

1. Не менять сохраняемые значения `red|orange|yellow|green|blue|purple|gray`.
2. Использовать одну таблицу цветов для меню, колонки и будущего overlay.
3. Не подменять нативные property handlers Office, изображений, музыки и
   других форматов: это может сломать их штатные метаданные.
4. Каждый эксперимент сначала проводить на одном тестовом расширении и одном
   тестовом каталоге.
5. После каждого изменения регистрации иметь симметричный uninstall и backup.
6. Не внедрять новый код в `explorer.exe`, пока out-of-process путь не исчерпан.
7. Не объявлять механизм рабочим по логам: нужен визуальный результат в
   Explorer и проверка обновления после назначения и удаления тега.

# Этап 1 — цветной emoji-кружок в штатной колонке Tags

Это первая задача.

## 1.1. Исправить контракт свойства

`System.Keywords` имеет тип `VT_VECTOR | VT_LPWSTR`. Property handler должен
возвращать корректный vector PROPVARIANT, а не одиночный `VT_LPWSTR`.

Хранилище остаётся прежним:

```text
:ColorTag = red
```

Property handler преобразует значение только при чтении для Explorer:

```text
red    -> 🔴
orange -> 🟠
yellow -> 🟡
green  -> 🟢
blue   -> 🔵
purple -> 🟣
gray   -> ⚪ или серый ресурс после визуальной проверки
```

CLI не должен записывать emoji в ADS.

## 1.2. Проверить три представления

В одном и том же тестовом файле последовательно проверить:

1. `Red` — контрольный текст;
2. `🔴 Red` — цвет и читаемая подпись;
3. `🔴` — компактный вариант, максимально похожий на меню.

Для каждого варианта зафиксировать:

- виден ли реальный цвет, а не монохромный glyph;
- нет ли квадрата-заглушки;
- не обрезается ли значение узкой колонкой;
- обновляется ли значение сразу после команды меню;
- исчезает ли оно после `Remove tag`;
- сохраняются ли сортировка и поиск по Tags;
- одинаков ли результат в светлой и тёмной теме.

## 1.3. Ограниченный способ установки

Первый spike регистрировать только для одного расширения без нативного
property handler. Не запускать массовую регистрацию десятков расширений, пока
визуальный результат не подтверждён.

## Гейт 1

Успех:

- кружок полноцветный;
- все семь цветов различимы;
- назначение и удаление обновляют колонку без ручного перезапуска Explorer;
- property handler не ломает другие свойства тестового типа.

Если `🔴` полноцветный и визуально приемлемый, это становится основным v1
вариантом колонки. Переходим к расширению покрытия, не усложняя схему.

Если emoji монохромный, заменяется квадратом или нестабилен, не пытаться
красить обычный символ `●`: цвет текста колонки задаёт Explorer. Перейти к
этапу 2.

# Этап 2 — настоящий ресурсный кружок через custom property schema

Цель: проверить штатный механизм перечислений Property System, где каждому
значению соответствует изображение из DLL.

Документированный механизм:

- собственное свойство, например `ColorTags.Explorer.Color`;
- enum-значения для семи цветов;
- элемент `image` / `IPropertyEnumType2::GetImageReference`;
- ссылка вида `ColorTagsMenu.dll,-101` на тот же ресурс, который использует
  контекстное меню.

## 2.1. Bounded spike

1. Создать отдельный `.propdesc` с новым PKEY и типом, подходящим для enum.
2. Добавить семь enum-значений и семь image references.
3. Возвращать новое свойство из существующего property handler.
4. Зарегистрировать схему только для тестового окружения.
5. Добавить колонку `Color Tag` в Details view и проверить фактический рендер.

## 2.2. Текущее состояние spike — 24 сентября 2026

- Property handler возвращает оба свойства: штатное `System.Keywords` и
  скалярное `ColorTags.Explorer.Color`.
- Нативный smoke test подтверждает чтение и запись стабильных значений цветов,
  а также загрузку ресурсов 101–107 из DLL.
- HKLM mapping для тестового расширения `.cttagtest` установлен.
- Файл `ColorTags-column-spike.propdesc` скопирован в `ProgramData`, и запись
  схемы появилась в `PropertySystem\PropertySchema`.
- Схема пока не прошла runtime-гейт: `PSGetPropertyDescriptionByName` и
  `PSGetPropertyDescription` возвращают `TYPE_E_ELEMENTNOTFOUND`. Поэтому
  Explorer ещё не знает колонку `Color Tag`; пустая колонка сейчас не является
  результатом проверки `IconList`.

Следующая диагностика выполняется ступенчато на новом тестовом PKEY:

1. Зарегистрировать минимальную строковую схему без enumeration и изображений.
2. После успешного lookup добавить `displayType="Enumeration"` и enum-значения.
3. Затем добавить `image` references и проверить `IPropertyEnumType2`.
4. Последним включить `drawControl="IconList"` и проверить Details View.

Каждая ступень обязана пройти программный lookup до открытия Explorer. Это
исключит ситуацию, когда запись схемы есть в реестре, но Windows молча отбросила
само описание свойства.

### Результат ступенчатой проверки

- Минимальная строковая схема прошла `PSGetPropertyDescription`.
- Найдена причина прежнего отказа: установленная версия Property System
  принимает `displayType="Enumerated"`; значение `Enumeration` приводило к
  `INPLACE_S_TRUNCATED (0x000401A0)` и отсутствующему property description.
- Enumeration без изображений прошла программный lookup.
- Финальная схема `ColorTags.Explorer.ColorIcon` с семью image references и
  `drawControl="IconList"` прошла lookup и проверку всех ресурсов 101–107.
- Shell API возвращает правильные стабильные значения `red` ... `gray` для
  семи `.cttagtest` файлов.
- `IColumnManager` добавил `ColorTags.Explorer.ColorIcon` в набор видимых
  колонок отдельного тестового окна Explorer.

Визуальный гейт закрыт отрицательно: Details View показывает текст для
`Enumerated`, но оставляет `IconList` пустым, хотя schema API возвращает семь
валидных image references и ресурсы DLL загружаются. Штатный путь к цветной
иконке в пользовательской колонке закрыт для этой версии Windows.

Регистрация property schema требует elevation. Для spike допустим один UAC,
но installer обязан уметь полностью отменить регистрацию.

## Гейт 2

Успех:

- Explorer действительно рисует resource image в ячейке Details view;
- кружок совпадает с ресурсом меню;
- сортировка опирается на стабильное значение цвета;
- uninstall удаляет схему и возвращает систему в исходное состояние.

Стоп-условие:

Если Explorer использует image reference только в других поверхностях и в
колонке всё равно показывает текст, закрыть этот путь как проверенный и не
углубляться в недокументированные column hooks.

# Этап 3 — решить покрытие файлов и папок

Даже успешная колонка не считается универсальной автоматически.

Нужно составить матрицу:

| Объект | Пример | Ожидаемый путь |
|---|---|---|
| Файл без нативного handler | `.txt`, `.md` | ColorTags property handler |
| Файл с нативным handler | `.jpg`, `.mp3`, Office | не заменять штатный handler |
| Папка | `Directory` | проверить отдельно; extension handler неприменим |
| NTFS | локальный файл/папка | ADS |
| FAT/exFAT/cloud virtual | файл/папка | SQLite fallback |

Отдельно исправить расхождение: Python/Core умеет ADS и SQLite, а нативный
property handler сейчас читает только ADS. Визуальный слой обязан использовать
тот же результат, что `TagService`, либо честно отключаться для fallback-хранилища.

## Гейт 3

Если штатная колонка покрывает нужные типы без замены чужих handlers, расширить
регистрацию постепенно.

Если она остаётся полезной только для части файлов, сохранить её как быстрый
официальный путь и перейти к этапу 4 для папок и остальных форматов.

# Этап 4 — внешний кружок для универсального покрытия

Использовать уже подтверждённую связку:

```text
UI Automation row name + rectangle
                +
Shell item name -> filesystem path
                ↓
TagService.GetTag(path)
                ↓
click-through companion overlay
```

Первая версия рисует только небольшой кружок в области колонки Tags. Она не
красит всю строку.

## Прогресс этапа 4 — 24 сентября 2026

- Реализован `src/Visual/ColorTagsOverlay.ps1`: отдельное прозрачное окно с
  `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`, которое не принимает ввод.
- Overlay находит строки через UI Automation, сопоставляет их с Shell items и
  читает стабильный ID напрямую из ADS `:ColorTag`.
- Цвета взяты из фактических PNG-ресурсов меню, а не из приблизительной
  палитры.
- Цветной круг выровнен по штатному glyph в колонке `Tags` и полностью
  перекрывает его серый рендер.
- Добавлены отдельные скрипты запуска и остановки. Процесс скрыт и рисует
  только когда нужное окно Explorer находится на переднем плане.
- Процесс автоматически перепривязывается к активному окну Explorer и читает
  его текущую папку; фиксированный тестовый каталог больше не обязателен.
- Каждый открытый Explorer теперь получает собственное окно overlay; проверены
  два одновременных окна с девятью цветными индикаторами.
- Overlay привязан к z-order своего Explorer и больше не рисуется поверх
  контекстного меню.
- Эксперимент с фоновым плавным `SetWindowPos` отклонён: даже после ограничения
  частоты он дважды приводил к зависанию Explorer. Overlay обновляет положение
  только основным безопасным циклом; плавное перемещение требует другой
  архитектуры без фоновых вызовов к окнам Проводника.
- Начата замена на `src/VisualNative/ColorTagsOverlayNative.cpp`. Нативный
  out-of-process помощник держит все HWND и `UpdateLayeredWindow` в одном
  UI-потоке, получает перемещение через `SetWinEventHook`, объединяет частые
  события и выполняет UI Automation/чтение ADS на отдельном STA-потоке.
- Первый ограниченный smoke test нашёл одно окно Explorer и 15 цветных тегов,
  завершился с кодом 0; Explorer остался отзывчивым. Автозапуск пока не включён.
- Событийное перемещение проверено отдельным тестом: Explorer был сдвинут на
  48 px, overlay за 250 мс переместился ровно на 48 px без отклонения по Y,
  после чего окно восстановлено, процесс мягко остановлен, Explorer отвечает.
- Прокрутка переведена с одного опроса раз в 500 мс на события изменения
  положения строк, значения scrollbar и начала/конца scrolling. Быстрые
  проходы ограничены 30 Гц и используют кэш Shell items; тестовая прокрутка
  вызвала немедленный быстрый проход и корректно убрала ушедшие со страницы
  индикаторы.
- Для колеса и touchpad добавлен ранний out-of-process `WH_MOUSE_LL`: слой
  сразу сдвигается по wheel delta, высоте строки и системному числу строк на
  один notch, а UI Automation позже уточняет результат. Тест трёх быстрых
  событий дал суммарный сдвиг −216 px за 72 мс; одиночное событие срабатывало
  за 8 мс. Предсказанный слой обрезается границами списка файлов.
- Результаты сканирования теперь помечаются поколением содержимого. Если
  PageDown, Home или scroll произошёл во время сканирования, устаревший снимок
  отбрасывается и больше не возвращает кружки на старые строки. В текущем
  регрессионном прогоне три wheel-события дали сдвиг −216 px за 76 мс,
  PageDown скрыл слой за 12 мс, Home восстановил его после перестроения.
- Прогноз wheel ограничен реальными `VerticalScrollPercent` и
  `VerticalViewSize` списка. На первой или последней строке слой больше не
  продолжает движение, когда содержимое уже стоит. Автотест верхней границы
  подтвердил смещение 0 px; обычный прогноз сохранил задержку 62 мс.
- Исправлено голодание полного прохода: непрерывная очередь scroll-событий
  раньше могла бесконечно откладывать перестроение кэша, из-за чего кружки не
  возвращались после прокрутки. Теперь дедлайн полного прохода имеет приоритет.
  Тест `верх → низ → верх` подтвердил восстановление всех 19 кружков.
- Глобальное скрытие overlay при правом клике удалено. Окна остаются owned
  popup без `topmost`, поэтому меню находится выше них, а кружки на остальных
  строках не исчезают. Автотест подтверждает видимость слоя при открытом меню.
- Во время 500-мс окна wheel-прогноза больше не запускается серия результатов,
  которые всё равно отбрасывались. Четыре wheel-события теперь дают ноль
  лишних fast scans. Первый видимый сдвиг выполняется прямо в wheel-hook за
  15 мс, готовый bitmap перемещается без повторного `UpdateLayeredWindow`, а
  короткая UI-анимация синхронизирует его с плавным движением строк Explorer.
- Финальный скачок устранён заменой высоты прямоугольника строки (24 px) на
  фактический шаг между строками (28 px): три wheel-импульса теперь дают ровно
  −252 px вместо −216 px. Для новых строк строится буфер на страницу вверх и
  вниз по реальным координатам `IFolderView::GetItemPosition`, включая
  сортировку и интервалы групп.
- Практическая проверка показала, что даже с точным шагом внешний слой не может
  покадрово совпасть с внутренней анимацией и виртуализацией строк Explorer:
  оставались финальный скачок и позднее появление новых кружков. Wheel-прогноз
  отключён. Теперь слой скрывается на время движения и восстанавливается одним
  точным UI Automation проходом через 120 мс после последнего wheel-события.
  Автотест: скрытие за 20 мс, восстановление за 142 мс, Explorer отвечает.
- Перед цветным кругом стирается штатный emoji небольшим фрагментом актуального
  фона строки. Это устраняет розовую обводку системного emoji, включая
  выделенную строку и тёмную тему.
- От непрозрачной erase-плашки и обработки `WM_MOUSEMOVE` отказались: они
  создавали квадрат при hover и мешали wheel-прогнозу. Цветной диск увеличен на
  4 px и перекрывает штатный glyph непрозрачной центральной областью, оставляя
  фон строки полностью прозрачным.
- Снимок реального окна подтвердил семь цветных кружков после удаления трёх
  диагностических колонок.

Остаётся проверить длительную навигацию и переключение вкладок, затем пройти
30-минутный smoke test.

## Требования

- отдельный процесс, без Windhawk и DLL-инъекции;
- `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`, чтобы слой не перехватывал мышь и
  клавиатуру;
- показывать кружки во всех видимых окнах Explorer;
- отслеживать scroll, sort, resize, column reorder, navigation и tabs;
- корректно работать при 100%, 125%, 150% DPI;
- не рисовать поверх меню, диалогов и других приложений;
- поддерживать несколько окон Explorer;

## Прогресс этапа 5 — 30 сентября 2026

Контракт вынесен в `src/Shared/ColorTagsConfig.h`. Один header-only заголовок
держит семь id, цвета из фактических PNG-ресурсов меню, названия по умолчанию
и номера иконок. Его читают контекстное меню, property handler и нативный
overlay. Цвет текста на цветной подложке считается по контрасту WCAG, а не
задаётся вручную, чтобы выбор оставался верным при любой пересборке иконок.

Пользовательские настройки лежат в `HKCU\Software\ColorTags` рядом с уже
существующими `PythonPath` и `ProjectRoot`:

```text
DisplayMode   REG_DWORD   0 = кружок, 1 = метка
Labels\<id>   REG_SZ      название тега
```

Реестр выбран вместо файла конфигурации: оба потребителя уже читают этот ключ,
в C++ не нужен парсер, а PowerShell, Python и будущий трей правят его без общей
библиотеки. Переименование не трогает хранилище — в ADS остаются стабильные id.

### Решение о гибридном отображении

Property handler теперь возвращает в `System.Keywords` пользовательское
название вместо emoji. Emoji закрыт отрицательно ещё на этапе 1, а текст
Explorer рисует сам — значит он не отстаёт ни при прокрутке, ни при
перетаскивании окна, сортируется и ищется штатными средствами.

Цвет остаётся за overlay. Причина разделения принципиальная: внешний процесс
узнаёт о движении содержимого из UI Automation событий уже после того, как
Explorer отрисовал кадр, поэтому покадровая синхронизация недостижима — это
подтверждено двумя отклонёнными экспериментами этапа 4. Слой по-прежнему
прячется на время движения, но теперь под ним остаётся штатный текст тега.
Быстрая прокрутка гасит только цвет, а не индикатор целиком.

Шрифт метки берётся из системного UI-шрифта, которым Explorer рисует список,
чтобы переход между двумя состояниями выглядел как смена цвета, а не как
подмена текста.

### Что осталось по этапу 5

- Трей-меню: переключение режима, редактор названий, автозапуск, выход.
- Хинт при наведении для режима кружка — по таймеру `GetCursorPos`, не
  расширением `WH_MOUSE_LL`: low-level hook вызывается на каждое движение мыши
  и при превышении `LowLevelHooksTimeout` снимается системой молча.
- Визуальная проверка: попадание метки в ячейку, поведение на узкой колонке,
  светлая и тёмная тема, 125% и 150% DPI.

## Этап 1 перепроверен — 30 сентября 2026

Вывод подтверждён. Windows 11 рисует эти emoji в колонке Details view
монохромным глифом.

Перепроверка была обоснованной: монохромный рендер цветного шрифта — это
поведение GDI, а DirectWrite рисует такие символы в цвете, и Проводник
показывает цветные emoji в именах файлов. Прежнее измерение к тому же делалось

## Этап 2 переоткрыт — 30 сентября 2026

Прежний вывод «Details View оставляет IconList пустым, штатный путь к цветной
иконке закрыт» **опровергнут**. Он держался на сравнении двух схем, которые
отличались пятью параметрами сразу, и пустая ячейка была прочитана как
доказательство того, что механизм не поддерживается.

Сами файлы схем при перепроверке оказались корректными: `drawControl` —
дочерний элемент, а не атрибут; `image` вложен в `enum`; подстановка даёт
полный путь к модулю, а не голое имя. Ошибка была в методике эксперимента, не
в коде.

### Проба 1 — доходит ли drawControl до колонок

Свойство `ColorTags.Explorer.DrawControlProbe`: тип `UInt32`, обработчик
возвращает константу 60, схема просит `<drawControl control="Rating"/>`.
Никакой связи с тегами — проверяется ровно одно.

Результат: **колонка Details view нарисовала жёлтые звёзды**, а не число 60.

Отсюда следует, что колонки Details view применяют `drawControl` к
пользовательским свойствам и умеют рисовать в ячейке цветную графику, а не
только текст. Значит пустая ячейка `IconList` объясняется чем-то другим:
одним из пяти отличий той схемы, извлечением ресурса из DLL или тем, что
описание было отброшено при регистрации.

Попутно уточнено, чего стоят прежние наблюдения: пользовательское свойство не
появляется в диалоге «Подробнее», колонка добавляется только через
`IColumnManager`, а `PSRegisterPropertySchema` должен вернуть ровно `S_OK` —
`INPLACE_S_TRUNCATED` означает молча отброшенное описание.

### Проба 2 и далее — итог перепроверки

Проверено восемь схем. Регистрируется всё, кроме одного:

| Схема | image | drawControl | searchInfo | Личность | Регистрируется |
|---|---|---|---|---|---|
| Minimal | нет | нет | простой | новая | да |
| Enum | нет | нет | простой | новая | да |
| DrawControlProbe | нет | Rating | простой | новая | да |
| IconListNoDraw | есть | нет | полный | старая | да |
| IconListPlain / PlainFile | есть | нет | простой | старая | нет |
| IconList / IconFresh / IconProbe / NoIndex | есть | **IconList** | любой | любая | нет |

Вывод: `drawControl control="IconList"` эта версия Property System не
принимает. `PSRegisterPropertySchema` возвращает `S_OK`, а описание свойства
молча выбрасывается и не разрешается по имени. Проверено при новой и
использованной личности свойства, при полном и урезанном `searchInfo`, при
картинках из ресурсов DLL и из отдельных `.ico`. `Rating` в тех же условиях
принимается и рисует в колонке цветные звёзды.

### Что в прежнем выводе было неверно

Формулировка «Details View показывает текст для Enumerated, но оставляет
IconList пустым» описывала не то, что происходило. Пустая ячейка не была
результатом отрисовки: описание свойства не было зарегистрировано вовсе.

Трассировка обработчика это доказала прямо. Проводник запрашивает
`GetValue` для пользовательского ключа один раз на файл и получает тег.
Колонка остаётся видимой, потому что в настройках вида она хранится по
`PROPERTYKEY`, а не по имени, и продолжает существовать после того, как
описание исчезло. Отсюда и вид «значение есть, а ячейка пустая».

Два утверждения прежнего вывода опровергнуты:

- колонки Details view **применяют** `drawControl` к пользовательским
  свойствам и умеют рисовать в ячейке цветную графику;
- property handler **опрашивается** для пользовательских свойств, значение
  доходит.

Верным остаётся только итог: цветной кружок в колонке через штатную схему
недостижим — но по другой причине, чем считалось.

### Почему другие drawControl не спасают

Допустимые значения: `Default`, `MultiLineText`, `MultiValueText`,
`PercentBar`, `ProgressBar`, `Rating`, `StaticText`, `IconList`,
`BooleanCheckMark`. Цвет из них дают только `Rating` (золотые звёзды,
количество от 1 до 5) и `PercentBar` / `ProgressBar` (полоса, цвет которой
система выбирает сама по величине). Ни один не позволяет задать семь
произвольных цветов — для этого существует ровно `IconList`, и он отвергается.

### Что осталось в системе после спайка

Зарегистрированы схемы стадий `minimal`, `enum`, `drawcontrol`, `iconfresh` и
файлы в `ProgramData`, плюс обработчик свойств для `.cttagtest`. Снимается
через `unregister_column_spike.ps1`, который теперь чистит все стадии.

## Icon overlay handlers — закрыто по факту машины, 30 сентября 2026

Механизм реализован полностью: семь COM-классов в `tags_menu.cpp`, общий кэш
чтения ADS на все семь, симметричные register/unregister с отчётом о слотах.
Собирается без предупреждений. Визуальный гейт не проводился — путь закрыт
арифметикой раньше.

Фактическое состояние машины разработки:

```text
Занято 21 обработчик при системном лимите 15.
Первые 15 заняты: OneDrive (7), Google Drive (4), Яндекс.Диск (4).
Уже сейчас не рисуются: YandexDisk5, AccExtIco1-3, EnhancedStorageShell,
Offline Files.
`ColorTags Red` встаёт на 20-ю позицию и не рисуется никогда.
```

Windows сортирует записи по имени и берёт первые пятнадцать. Все, кто попал в
список, используют ведущие пробелы: у OneDrive их пять, у Google Drive и
Яндекс.Диска по четыре, у AccExtIco три. Чтобы попасть в лимит, ColorTags
должен обогнать их по числу пробелов, то есть вытеснить чужие значки
синхронизации — по одному за каждый свой цвет.

Вывод: путь закрыт не документацией, а состоянием реальной системы, и
открыть его можно только ценой чужих значков. Код оставлен в дереве: на
машине без трёх облачных клиентов он рабочий, и отчёт `-WhatIfSlots` сам
скажет, применим ли он.
