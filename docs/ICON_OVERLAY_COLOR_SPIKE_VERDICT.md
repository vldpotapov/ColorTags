## 1. Главный гейт: сколько overlay slots реально свободно (то, что вы просили первым)

Штатный Shell Icon Overlay механизм делит **ограниченный общий image-list слотов** (документировано
~15 общедоступных регистраций на shell), и все провайдеры конкурируют за них. Census этой машины:

| Провайдер-запись | Кол-во зарегистрированных |
|---|---|
| OneDrive1..7 | 7 |
| YandexDisk1..5 | 5 |
| Google Drive (Sync'd / Pooled / Working / Error…) | 4 |
| AccExtIco1..3 (антивирус/сторонний) | 3 |
| EnhancedStorageShell | 1 |
| Offline Files | 1 |
| **Итого уже зарегистрировано** | **21** |

Плюс системные/shell-собственные слоты, которые делят тот же лимит.

**Ключевой факт:** на этой системе **уже 21 зарегистрированный overlay identifier**
при документированном практическом лимите ~15 общих слотов → реестр **переподписан ещё до нас**.
Своих регистраций у проекта — **0** (не конфликтует с нашими CLSID, но и реюзать нечего: новый
overlay handler + COM регистрация пришлось бы строить с нуля).

### Verdict по слотам
- **0 дополнительных регистраций** гарантированно не вытесняют существующих (но и не рисуют ничего).
- **Каждая добавленная цветная точка = +1 регистрация** (1 идентификатор → 1 иконка-оверлей), и на
  переподписанной системе это **вытесняет чужой overlay** (в т.ч. OneDrive «синхронизировано»,
  гит-статус) или сам не рисуется.
- **7 цветов = 7 регистраций** → на этой машине **нельзя безопасно**: это гарантированно конфликтует
  с обычным окружением (ваш собственный stop-criterion).

## 2. Вписывается ли это в ваш stop-condition? — ДА

«…если 7 цветов требуют 7 системных overlay slots и это конфликтует с обычным Windows окружением,
**не ломать систему ради семи цветов**».

Доказано: 21 уже занято (>15), добавлять 7 → вытеснение OneDrive/гит-статусов или нереализуемые точки.
**Phase 8 (overlay-путь) = NOT SAFE / HIGH RISK** с обоснованием в слотах, а не в visual tree.

## 3. НО: сам механизм НЕ требует visual-tree identity (важное отличие)

`IShellIconOverlayIdentifier::IsMemberOf(pszPath, …)` вызывается Shell **с реальным путём файла/папки** —
identity поставляется штатно, **без рядов ItemsRepeater/DataContext**. То есть:

- If a machine НЕ переподписана (чистая Win11, мало провайдеров) — 3–4 цветные точки (🔴🟢🟡 + резерв)
  реально реализуемы штатным путём, production-safe, без визуального дерева.
- This machine переподписана → **мы сами по себе production-safe не можем** (не вина Explorer, но
  факт окружения).

## 4. Итоговый вердикт Phase 8 (overlay)

| Критерий | Факт |
|---|---|

| Folders: точка на иконке | **YES** (механизм умеет) |
| Requires visual-tree identity | **NO** (IsMemberOf даёт путь сам) |
| Slots required per color | **1 регистрация на цвет** |
| Available slots on test system | **переподписано: 21 зарегистрировано > ~15 лимита → 0 гарантированно свободных** |
| Conflict risk (OneDrive/Dropbox/Git…) | **HIGH** — при добавлении регистраций вытесняем существующих |
| Maximum safe colors (эта машина) | **0** (без вытеснения чужих) |
| Maximum safe colors (чистая Win11, мало провайдеров) | **~3–4** (вокруг OneDrive×1 + резерв) |
| Production risk | **HIGH** (зависит от окружения; на тестовой машине — не даёт добавить) |
| Recommendations | 7 цветов в Core + контекстное меню (все 7), а visual overlay ограничить числом слотов, которые реально свободны (обычно 0–4); не занимать слоты конкурентов |

## 5. Рекомендуемая production-safe схема (то, что вы сами описали)

1. **Все 7 тегов** живут в Core/Storage/TagService — **без изменений** (как и было). ✔ untouched
2. **Контекстное меню** показывает все 7 цветов — identity файла там **доказана живой** (Phase 5/8 метод).
3. **Icon overlay**: показывать **только то количество цветов, которое реально помещается** в
   свободные слоты на конкретной машине (validate count при старте: считать занятые → cap).
   Никогда не 7 на переподписанной системе.
